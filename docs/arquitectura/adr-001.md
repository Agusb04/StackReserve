# ADR 001: Recorte backend con Spring Boot, arquitectura en capas y persistencia en memoria

## Contexto

El ejercicio 3 requiere una primera versión ejecutable del sistema de gestión de turnos de una biblioteca académica. El objetivo es demostrar el flujo completo de dominio —consultar disponibilidad, reservar, cancelar, registrar asistencia— sin introducir complejidad operativa innecesaria. No se requiere integración con sistemas externos, autenticación real ni base de datos persistente en esta iteración.

Las prioridades de los interesados para esta iteración son dos capacidades concretas: **consultar la disponibilidad de salas para un día determinado** (`@disponibilidad-salas`) y **cancelar una reserva confirmada** (`@cancelacion-reserva`).

## Decisión

Se adopta un backend **Spring Boot 3.3 con JDK 21**, organizado en una **arquitectura en capas clásica** (Controller → Service → Repository → Domain) con las siguientes decisiones específicas:

### Dominio sin ORM

Las entidades del dominio (`Sala`, `Turno`, `Reserva`, `Estudiante`, `HistorialEstado`) son POJOs simples sin anotaciones JPA. Esto reduce la fricción de configuración en la iteración inicial y mantiene el foco en las reglas de negocio.

### Persistencia en memoria con HashMap

Los repositorios (`SalaRepository`, `ReservaRepository`, `EstudianteRepository`) implementan su propio almacenamiento en `HashMap`. Esto elimina la necesidad de configurar una base de datos externa o un ORM. El ciclo de vida de los datos está acotado a la ejecución de la aplicación, lo cual es suficiente para esta iteración.

### API REST JSON

La interfaz pública es REST JSON, verificable desde los step definitions de Cucumber con `TestRestTemplate` atravesando el stack HTTP completo.

### BDD ejecutable con Cucumber JVM + JUnit Platform Suite

Cada historia priorizada tiene un archivo `.feature` 1:1. Los step definitions entran por los endpoints REST sin saltear capas. El glue está en `ar.edu.fiuba.is1.tpi.bdd` e incluye los subpaquetes `steps`.

### Sin autenticación implementada

RN-08 (autenticación vía sistema institucional) queda fuera del alcance de esta iteración según el documento de requisitos. El sistema asume usuarios autenticados.

## Consecuencias positivas

- Arranque inmediato sin infraestructura adicional: solo `./gradlew check`.
- Ciclo de retroalimentación corto para validar reglas de negocio.
- Separación de responsabilidades verificable en los tests: Controller → Service → Repository → Domain.
- Las features priorizadas (`@disponibilidad-salas`, `@cancelacion-reserva`) quedan completamente cubiertas con escenarios ejecutables.

## Consecuencias negativas

- Los datos no se persisten entre reinicios (aceptable para esta iteración).
- Los repositorios HashMap no son thread-safe; en una iteración posterior se reemplazarían por Spring Data JPA con H2 o PostgreSQL.
- La lógica FCFS se implementa mediante procesamiento secuencial de solicitudes ordenadas, sin garantías de atomicidad ni manejo de concurrencia real.
